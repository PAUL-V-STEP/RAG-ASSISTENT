Единое техническое задание для исполнителя (Cursor). Проект: RAG-ассистент по руководству ТО автолифта АЛ 3У-М6, ветка `assistant_api`.

Документ заменяет целиком:
- задание v4 «Contextualization и Canonicalization вопросов для RAG-ассистента АЛ 3У-М6» (и v1–v3);
- ТЗ версии 2 «Уровень проверенных ответов (Q-A) перед RAG и утилита qa_tool».

Ссылки на эти документы и на их нумерацию разделов больше не действуют. Нумерация ниже — единая. История изменений — в приложении D.

Все факты о технике и обслуживании берутся **только** из файлов АЛ 3У-М6 в корне проекта. Параметры, которых там нет, не выдумывать: давление в МПа, моменты затяжки в Н·м, ТО-2 и т. п.

# Часть I. Общие положения

## 1. Цель

Добавить в API-ветку RAG-ассистента предварительную обработку вопроса и уровень проверенных ответов:

1. **Коррекция ввода** — исправление текста, набранного в латинской раскладке вместо кириллицы, с включённым Caps Lock или со смешением похожих латинских и кириллических букв. Если исправление однозначно, оно применяется автоматически; если нет — исправленный вариант предлагается пользователю на подтверждение (раздел 9).
2. **Contextualization** — переписывание вопроса в самостоятельный (standalone) с учётом истории диалога собственным вызовом LLM со structured output (раздел 10).
3. **Canonicalization** — каноническая форма вопроса из слотов по глоссарию документа для точного кэша и фильтров семантического кэша (раздел 11).
4. **Уровень проверенных ответов (Q-A)** перед RAG: если вопрос надёжно совпадает с записью базы Q-A, выдаётся проверенный ответ (`direct`) или он передаётся в генерацию как приоритетный контекст (`hybrid`); иначе вопрос уходит в RAG (раздел 13). Ложное совпадение хуже, чем ответ RAG.

Также нужно:
- подключить базу знаний АЛ 3У-М6 к API-пайплайну и добавить историю диалога (сейчас её нет);
- адаптировать существующий семантический кэш, не переписывая его (раздел 12);
- сделать утилиту `qa_tool` для создания базы Q-A, её проверки, ручного и автоматического тестирования, статистики и очистки (раздел 15);
- вынести **все пороги кэша и уровня Q-A, все режимы основного приложения и утилит в переменные окружения** (раздел 6);
- сделать **режим трассировки**, в котором отдельным блоком видно, как вопрос преобразуется от исходной формулировки до промпта, отправленного в LLM (раздел 16);
- сделать **пакетное автоматизированное тестирование** с чтением вопросов из файла (раздел 17);
- написать подробный **README** с описанием всех этапов обработки запроса (раздел 20).

## 4. Базовая линия и флаги

- **Базовая линия** — `assistant_api` с `DATA_FILE` = RAG V3, всеми флагами нормализации `false` и `QA_LAYER_ENABLED=false`. С ней сравниваются все результаты. Сравнивать с текущим поведением на `docs.txt` бессмысленно: меняется база знаний.
- Подключение RAG V3 — отдельный коммит до нормализации. В нём:
  - путь к `DATA_FILE` вычисляется от корня проекта (`Path(__file__).resolve().parent.parent / DATA_FILE`) и работает при запуске из `assistant_api`; допускается и абсолютный путь; имя файла с пробелами и кириллицей не переименовывать;
  - коллекция Chroma явно удаляется и создаётся заново (или создаётся новая коллекция с `kb_version` в имени). Условие `collection.count() == 0` само по себе не годится: старые чанки ML/NLP останутся;
  - после пересборки проверяется, что все чанки взяты из RAG V3, а чанков из `docs.txt` и файла вопросов-ответов нет;
  - для вопросов q01–q25 (приложение A.1) в `reports/baseline_answers.json` сохраняются ответы, id и тексты найденных чанков. Удобно сделать это пакетным прогоном (раздел 17) с профилем `env/baseline.env`.
- Автотестов в проекте нет. Базовая линия проверяется по `reports/baseline_answers.json` (при флагах `false` для q01–q25 ретривер должен вернуть те же id чанков; тексты ответов LLM могут отличаться) и по `git diff --stat -- assistant_giga` (пусто).
- **При выключенных флагах:** ретривер получает исходный вопрос, промпт генерации не меняется, история копится, но в ретривер и генерацию не подмешивается. Кэш работает по текущей схеме (хеш сырого вопроса + косинусный поиск), только с изоляцией по `kb_version`.
- **При включённых флагах:** ретривер получает только `standalone`, генерация — `raw` + `standalone` + чанки + краткую историю (последние `HISTORY_TURNS` пар, ответы обрезаны до `HISTORY_ANSWER_MAX_CHARS`). Шаблон промпта для этого режима — `prompts/generate_extended_ru.txt` (один шаблон с необязательными блоками истории и проверенного ответа, 13.10). Исходный шаблон не меняется и используется при всех выключенных флагах.

## 5. Целевой пайплайн

```
вопрос + история + DialogState
  │
  ├─ [0] raw                         — исходный текст, сохраняется без изменений
  ├─ [1] clean_text()                — NFKC, пробелы, ё→е, единицы, варианты ТО          (10.1)
  ├─ [2] fix_input()                 — похожие буквы, Caps Lock, латинская раскладка      (9)
  │        ├─ auto     → дальше с исправленным текстом
  │        ├─ confirm  → «Вы имели в виду: …?»  → ответ пользователю, дальше не идём
  │        └─ none     → дальше с исходным текстом
  ├─ [3] needs_history()             — фильтр без LLM                                     (10.2)
  │        ├─ да  → [4] contextualize()  — LLM, JSON по схеме                              (10.3)
  │        └─ нет → standalone = текст после [2]; topic_switch по слотам                   (10.6)
  ├─ [5] validate_rewrite()                                                               (10.4)
  ├─ needs_clarification? → уточняющий вопрос; Q-A, кэш и ретривер не вызываются
  ├─ [6] canonicalize()              — слоты по глоссарию → canonical, cache_key          (11)
  ├─ [7] QA LAYER                                                                          (13)
  │        ├─ стоп-правила вне корпуса → none
  │        ├─ точное совпадение по canonical → семантический поиск → слоты и отрыв
  │        ├─ direct → проверенный ответ, генерация не вызывается ──────────────┐
  │        ├─ hybrid → [9] ретривер + [10] генерация (шаблон с блоком Q-A)      │
  │        └─ none   → дальше                                                    │
  ├─ [8] exact cache (cache_key) → semantic cache (вектор standalone + фильтры)    (12)
  ├─ [9] retrieval(standalone)                                                    │
  ├─ [10] сборка промпта → LLM                                                    │
  └─ [11] ответ ← ─────────────────────────────────────────────────────────────────┘
        update_state(), запись в кэш (кроме direct/hybrid), запись в историю, лог, трассировка (16)
```

Номера шагов `[0]–[11]` одинаковы в коде (`step_id`), в логе (раздел 18), в блоке трассировки (раздел 16) и в README (раздел 20).

Правила:
- Уровень Q-A работает с `standalone` и слотами из нормализации. Если нормализация выключена (`NORMALIZATION_ENABLED=false`), используется текст после шага [2]: точное совпадение не проверяется, работает только семантический поиск, слоты извлекаются `canonicalize()` без LLM.
- Ответы `direct` и `hybrid` не записываются в семантический кэш: источник истины для них — база Q-A.
- В историю диалога ответ уровня Q-A записывается так же, как ответ RAG.
- Шаг [2] выполняется всегда, когда `INPUT_FIX_ENABLED=true`, даже при выключенной нормализации: исправленный текст получает и обычный RAG.

## 6. Переменные окружения

### 6.1. Правила

1. **Все пороги кэша и уровня Q-A, все лимиты и таймауты, все режимы основного приложения и утилит, все пути** задаются переменными окружения. Полный список — 6.3. Константы-пороги в коде запрещены (кроме значений по умолчанию в модуле конфигурации).
   Имя порога содержит метрику: `*_MIN_SIMILARITY` — сходство (попадание при значении ≥ порога), `*_MAX_DISTANCE` — расстояние (попадание при значении ≤ порога). Безымянные `*_THRESHOLD` не используются.
2. Единый модуль `assistant_api/settings.py`: читает переменные один раз при старте, приводит типы, проверяет диапазоны и допустимые значения и отдаёт неизменяемый объект `Settings`. Модули `normalization`, `qa_layer`, `batch`, кэш и консоль получают значения только из него.
3. **Приоритет источников** (от высшего к низшему):
   1. флаг командной строки утилиты (`--mode full`), если он есть;
   2. переменная окружения процесса;
   3. файл профиля, указанный в `ENV_FILE` (например, `env/full.env`);
   4. `.env` в корне проекта;
   5. значение по умолчанию в `settings.py`.

   `.env` и `ENV_FILE` читаются через `python-dotenv`, если он уже есть в проекте. Если его нет, — простым парсером `KEY=VALUE` (строки `#` — комментарии), новую зависимость не добавлять.
4. **Каждый флаг командной строки** `qa_tool` и пакетного прогона имеет переменную-двойник (6.3, группы «Утилита qa_tool» и «Пакетный прогон»). Флаг только переопределяет её на один запуск.
5. Ошибка значения (не число, вне диапазона, неизвестный режим) — остановка при старте с сообщением: имя переменной, значение, допустимые значения, источник. Молчаливой подстановки значения по умолчанию нет.
6. **Профили.** В каталоге `env/` — готовые файлы:
   - `baseline.env` — все флаги нормализации, коррекции ввода и Q-A выключены (базовая линия, раздел 4);
   - `normalize.env` — нормализация включена, Q-A выключен;
   - `qa_shadow.env` — нормализация и Q-A в режиме `shadow`;
   - `full.env` — всё включено, `QA_MODE=full`;
   - `debug.env` — как `full.env` плюс `TRACE_MODE=full`.
7. **Просмотр конфигурации.** `python -m assistant_api.app --print-config` и `qa_tool config` выводят таблицу: переменная, значение, источник (`cli` / `env` / `ENV_FILE` / `.env` / `default`). Секреты (`*_KEY`, `*_TOKEN`, `*_SECRET`, `*_PASSWORD`) маскируются: `sk-…a1b2`. Та же таблица пишется в начало каждого отчёта (`reports/…`) и в начало файла трассировки.

# Часть II. Нормализация вопроса

## 9. Коррекция раскладки и регистра — `fix_input()`

Шаг [2]. Выполняется после `clean_text()` и до всех остальных шагов, без LLM. Модуль `normalization/input_fix.py`. Управляется переменными группы «Коррекция ввода» (6.3).

### 9.1. Какие ошибки исправляются

| Вид | Пример ввода | После исправления | Порядок |
|---|---|---|---|
| `homoglyph` — латинские буквы, похожие на кириллические, внутри русского слова | «TО-1» (латинская T), «Cкoлько» | «ТО-1», «Сколько» | 1 |
| `capslock` — включённый Caps Lock | «кАК ЧАСТО ПРОВОДИТСЯ то-1?» | «Как часто проводится ТО-1?» | 2 |
| `layout` — русский текст набран в латинской раскладке | «Rfr xfcnj ghjdjlbncz NJ-1&» | «Как часто проводится ТО-1?» | 3 |
| `layout` (обратная) — латинский термин из белого списка набран в русской раскладке | «Как обслуживается шасси Феупщ?» | «Как обслуживается шасси Atego?» | 3 |

Исправления применяются по порядку: Caps Lock на латинице («rFR XFCNJ…») сначала инвертируется, затем исправляется раскладка. После исправления текст ещё раз проходит `clean_text()` (ё→е, единицы, варианты ТО).

### 9.2. Похожие буквы (`homoglyph`)

- Токен, в котором есть кириллица и латиница, а все латинские буквы входят в набор похожих (`A B C E H K M O P T X a c e o p x y`), приводится к кириллице.
- Токен, в котором большинство букв латинские, а кириллические — похожие, и результат замены входит в белый список (`Atego`, `Mercedes-Benz`), приводится к латинице.
- Исправление всегда автоматическое: оно не меняет смысла, но без него «TО-1» не совпадёт с термином глоссария и ключ кэша будет другим.

### 9.3. Caps Lock (`capslock`)

- **Инвертированный регистр**: у не менее 60 % слов длиной от 3 букв первая буква строчная, остальные заглавные («кАК», «чАСТО»), — `swapcase()` всего текста.
- **Весь текст заглавными** (не менее 10 букв, из них не менее 90 % заглавных) — перевод в нижний регистр с заглавной первой буквой.
- После исправления восстанавливается регистр аббревиатур глоссария и белого списка: ЕО, ТО-1, СО, КОМ, АКБ, ГОСТ, ATEGO.
- Исправление автоматическое.

### 9.4. Раскладка (`layout`)

1. **Кандидаты.** Токены с латинскими буквами, кроме:
   - слов из `LAYOUT_LATIN_WHITELIST_FILE`. Белый список собирается при сборке глоссария из латинских слов `DATA_FILE` и глоссария (ATEGO, Atego, Mercedes-Benz, Mercedes) плюс ручные дополнения;
   - единиц измерения (`°C`) и токенов из одних цифр и знаков.
2. **Преобразование.** Посимвольно по раскладке ЙЦУКЕН, включая знаки на месте русских букв: `[`→х, `]`→ъ, `;`→ж, `'`→э, `,`→б, `.`→ю, `` ` ``→ё. Последний знак токена решается по словарю: «hf,jxe.» → «рабочую», а «djls.» в конце предложения → «воды.». Конечные `&` и `?` → «?».
3. **Распознавание.** Слово считается распознанным, если результат:
   - известен `pymorphy3` (`word_is_known`);
   - или совпадает с термином или аббревиатурой глоссария (точно для аббревиатур, нечётко с `FUZZY_CUTOFF` для остальных);
   - или совпадает с термином из последних `HISTORY_TURNS` реплик истории.
4. **Доля.** `ratio = распознанные / кандидаты`. За каждое слово, совпавшее с глоссарием или историей, прибавляется `LAYOUT_CONTEXT_BONUS / кандидаты` (не выше 1). Так контекст делает исправление увереннее: «А для CJ?» после вопроса о ТО-1 однозначно означает «А для СО?».
5. **Решение:**

| Условие | Действие `InputFix.action` |
|---|---|
| кандидатов нет | `none` |
| `ratio ≥ LAYOUT_AUTO_MIN_RATIO` и (кандидатов ≥ `LAYOUT_MIN_LATIN_TOKENS` или есть совпадение с глоссарием) | `auto` — дальше с исправленным текстом |
| `LAYOUT_CONFIRM_MIN_RATIO ≤ ratio`, но условие `auto` не выполнено | по `LAYOUT_UNCLEAR_ACTION`: `confirm` (по умолчанию), `answer_with_note` или `ignore` |
| `ratio < LAYOUT_CONFIRM_MIN_RATIO` | `none`, в лог `layout_suspect`, если `ratio > 0` |

Нераспознанные слова при `auto` и `confirm` всё равно преобразуются (вероятная опечатка) и перечисляются в `unresolved_tokens`.

Ложных исправлений не должно быть: английское слово в русском вопросе («Как сделать reset ошибки?») даёт `ratio = 0` и остаётся как есть.

### 9.5. Подтверждение (`confirm`) и пометка (`answer_with_note`)

**`confirm`.** Вопрос не отправляется дальше. Пользователь получает:

```
Похоже, вопрос набран в латинской раскладке. Вы имели в виду:
«Как часто проволится ТО-1?»
Ответьте «да» или задайте вопрос заново.
```

- Исправленный текст сохраняется в `DialogState.pending_input_fix`, `needs_clarification=true`, `clarification_kind="input_fix"`.
- Ответ пользователя тоже проходит шаг [2]. Если после исправления это «да», «верно», «ага», «yes», «+» (латинское «lf» исправляется в «да»), обрабатывается сохранённый вопрос, как будто пользователь ввёл его сам.
- Любой другой ответ — новый вопрос, `pending_input_fix` сбрасывается.
- Q-A, кэш и ретривер на шаге подтверждения не вызываются, в кэш ничего не пишется.

**`answer_with_note`.** Вопрос обрабатывается с исправленным текстом, а ответ начинается строкой «Вопрос распознан как: «…»». Режим для пакетных прогонов и пользователей, которым не нужен лишний шаг.

**`ignore`.** Исправление не применяется, текст идёт дальше как есть.

### 9.6. Связь с остальными шагами

- `raw` всегда остаётся исходным. В `cleaned` и во всех следующих шагах используется `input_fix.text`.
- `validate_rewrite()` (10.4) сверяет числа и отрицания с `input_fix.text`, а не с `raw`: латинский `raw` не содержит русских отрицаний.
- Ключ кэша строится по исправленному тексту, поэтому «Rfr xfcnj ghjdjlbncz NJ-1&» и «Как часто проводится ТО-1?» дают один `cache_key`.
- Шаг [2] работает и при `NORMALIZATION_ENABLED=false`, если `INPUT_FIX_ENABLED=true`.
- Трассировка (раздел 16) показывает текст до и после, вид исправления, `ratio` и список заменённых слов.

Фикстуры — приложение A.6.

## 10. Contextualization

### 10.1. clean_text()

Шаг [1]. Выполняется до коррекции ввода (раздел 9) и повторно после неё.

- `unicodedata.normalize("NFKC")`, обрезка и схлопывание пробелов, ё→е, единые кавычки и тире.
- Регистр сохраняется в `cleaned` и `standalone`, нижний регистр только внутри канонизации.
- Единицы в корпусе: `°C`, `ч`, `мин`, `мл`, `л`, `%`. Нормализовать «градусов / град / °с» → `°C`, «минут / мин.» → `мин`, «часов / час.» → `ч`, «миллилитров» → `мл`, «литров» → `л`. Словарь `мпа→МПа`, `нм→Н·м` оставить, но в тестах на этом документе не требовать. Единицы словаря, которых нет в `DATA_FILE`, использует стоп-правило уровня Q-A (13.7).
- Варианты написания видов ТО: «ТО1», «ТО 1», «то-1», «техническое обслуживание № 1», «первое ТО» → `ТО-1`; «ежедневное обслуживание» → `ЕО`; «сезонное обслуживание», «сезонное» → `СО`. Таблица — в `glossary_extra.yaml`, не в коде.

### 10.2. needs_history()

Шаг [3].

Все проверки — **по токенам**, а не по подстрокам. Токенизация: текст после шага [2] в нижнем регистре, ё→е, разбиение по `[^\w-]+` (дефис остаётся внутри токена, поэтому «ТО-1» — один токен `то-1`).

Правила проверяются по порядку, первое сработавшее определяет результат:

1. История пустая → `False`.
2. **Первый токен** входит в множество `{а, и, еще, тогда, также}` → `True`. Сравнивается токен целиком: «Их нужно снимать?» (`их`) и «Интервал ТО-1?» (`интервал`) по этому правилу не проходят. Отдельный пункт «а если» не нужен: его покрывает «а».
3. Среди токенов есть местоимение или указатель: `он, она, оно, они, его, ее, их, ему, ей, им, ним, ней, них, этот, эта, это, эти, этого, этой, этим, тот, та, те, там, туда, здесь, тут, аналогично` → `True`. Сочетания «такой же», «то же», «тот же» проверяются как пары соседних токенов. Одиночный токен `то` в список не входит, чтобы не путать с аббревиатурой «ТО».
4. В вопросе нет ни одного **предметного** термина глоссария → `True`. Предметные термины — записи с `type` из `node`, `level`, `operation`, `part`, `topic` (раздел 11.1). Параметры и условия («трудоемкость», «периодичность», «температура», «зимой») предметными не считаются: без объекта такой вопрос не самодостаточен. Единицы («минут», «градусов») — тоже не термины.
5. Иначе → `False`.

Ограничения по числу слов нет: короткий вопрос с предметным термином («Какая периодичность ТО-1?») считается самодостаточным, а длинный без термина («Нельзя превышать сколько градусов?», «Не меньше скольки минут?») — зависимым.

Чтобы правило 4 работало, в `glossary_extra.yaml` должна быть запись `type: topic` для общего понятия «техническое обслуживание» (варианты «ТО», «обслуживание», «виды ТО»). Иначе вопросы вроде q01, q19, q20 будут ошибочно отправляться в LLM.

Тесты:
- все примеры приложения A.5;
- вопросы q01–q25 как отрицательные при непустой истории;
- поле `history_gate` во всех диалогах приложения A.2, где оно задано.

### 10.3. contextualize()

Шаг [4].

- Существующий клиент LLM `assistant_api`. Модель задаётся в `NORMALIZER_MODEL`, по умолчанию самая быстрая из доступных.
- `temperature = 0`, строго JSON. JSON Schema, если провайдер её поддерживает; иначе JSON mode, валидация Pydantic и до `NORMALIZER_RETRIES` повторных попыток с текстом ошибки.
- Таймаут `NORMALIZER_TIMEOUT_S` (по умолчанию 6 с, допустимо 5–8 с) → fallback, `fallback_reason="timeout"`.
- На вход: последние `HISTORY_TURNS` пар, ответы обрезаны до `HISTORY_ANSWER_MAX_CHARS` символов, `DialogState`, до 50 канонических терминов глоссария, вопрос.

Промпт `prompts/contextualize_ru.txt`:

```
Ты переписываешь вопросы пользователя к руководству по техническому обслуживанию автолифта АЛ 3У-М6.
Задача: сделать последний вопрос понятным без истории диалога.

Правила:
1. НЕ отвечай на вопрос. Только переформулируй.
2. Подставляй вместо местоимений и пропусков объекты из истории и состояния диалога.
3. Из ответов ассистента можно брать только объект, на который указывает местоимение
   («его», «эта промывка», «их» → фильтроэлемент, пальцы гидроцилиндров, Магос Унидем).
   Нельзя переносить значения, нормы, сроки, способы и критерии (числа, «вхолостую»,
   «по формуляру», «ниже нижней метки»), если пользователь сам их не назвал.
   Вопрос должен спрашивать, а не содержать ответ.
4. Не добавляй узлов, деталей, видов ТО и чисел, которых нет в истории или вопросе.
   Виды ТО в документе: только ЕО, ТО-1, СО.
5. Числа, единицы, отрицания и ограничения («не», «нельзя», «без», «кроме», «только»,
   «под давлением») сохраняй дословно.
6. Самостоятельный вопрос возвращай без изменений по смыслу. «Можно ли…» не меняй на «Запрещается ли…».
7. Новая тема → не переносить старый контекст, topic_switch=true.
8. Если ссылку можно отнести к двум и более объектам из истории, needs_clarification=true
   и короткий уточняющий вопрос с перечислением вариантов.
9. Используй термины глоссария, если они подходят по смыслу.
10. Определи intent и entities. maintenance_level — только ЕО, ТО-1, СО или null.

Состояние диалога: {state}
Термины глоссария: {glossary_terms}
История:
{history}
Вопрос: {question}

Верни только JSON:
{"standalone": "...", "intent": "...", "entities": {...},
 "depends_on_history": true|false, "topic_switch": true|false,
 "needs_clarification": true|false, "clarification_question": null|"..."}
```

Few-shot (7 примеров, только по документу, без МПа и ТО-2):

1. **Местоимение.** История: ТО-1 через 2 месяца или 250 ч работы гидросистемы. Вопрос: «А по часам гидросистемы через сколько его делают?» → «Через сколько часов работы гидросистемы проводится ТО-1 автолифта АЛ 3У-М6?»
2. **Эллипсис.** История: трудоемкость ТО-1 около 6 ч. Вопрос: «А для СО?» → «Какова трудоемкость СО автолифта АЛ 3У-М6?»
3. **Смена темы.** История: прогрев рабочей жидкости. Вопрос: «Какие средства нужны для уборки фургона?» → без переноса гидросистемы, `topic_switch=true`.
4. **Неоднозначность.** История: перечислены ЕО, ТО-1 и СО. Вопрос: «Какая у него трудоемкость?» → `needs_clarification=true`, «Уточните, для какого вида обслуживания: ЕО, ТО-1 или СО?»
5. **Самостоятельный.** История про трудоемкость ЕО. Вопрос: «При каком уровне масла в баке запрещена эксплуатация автолифта?» → без изменений по смыслу, `depends_on_history=false`, `topic_switch=true`.
6. **Отрицание без переноса ответа.** История: нормы гидрожидкости, в т. ч. «не выше 80 °C». Вопрос: «Нельзя превышать сколько градусов?» → «Какую температуру рабочей жидкости гидросистемы нельзя превышать?» Число 80 в standalone не переносится. Intent — `parameter_value` (правило 0 раздела 11.2), а не `safety`.
7. **Модальность «можно».** История: перечень запретов при ТО. Вопрос: «А без страхующих упоров платформу смотреть можно?» → «Можно ли осматривать поднятую платформу без страхующих упоров?», `intent=safety`. «Без» и «можно» сохраняются.

### 10.4. validate_rewrite()

Шаг [5]. Исходным вопросом здесь считается текст после шага [2] (`input_fix.text`), а не `raw`.

Переписывание отклоняется (используется текст после шага [2], `rewrite_source="fallback"`, причина в `fallback_reason`), если:
- число из исходного вопроса (`\d+(?:[.,]\d+)?`) отсутствует в standalone;
- в исходном вопросе есть отрицание («не», «нельзя», «без», «кроме», «только»; сравнение по токенам, не по подстроке), а в standalone нет ни одного из них и нет «запрещ»;
- в standalone появилось число, которого нет в исходном вопросе, но есть только в ответах ассистента (перенос ответа в вопрос);
- в standalone появилось «ТО-2» или вид ТО, отсутствующий в истории и вопросе;
- `len(standalone) > REWRITE_MAX_RATIO * max(len(input_fix.text), 30)`;
- standalone похож на ответ: «Ответ:», нумерованные шаги, больше двух предложений.

### 10.5. update_state()

После ответа (кроме случаев `needs_clarification`):
- `topic_switch=true` → сброс состояния и заполнение из новых entities;
- иначе непустые `node`, `operation`, `part`, `maintenance_level` перезаписывают поля.

`entities` здесь — результат `canonicalize()` (слоты по глоссарию, раздел 11.3), а не сырой ответ LLM. Поэтому состояние заполняется одинаково и при вызове LLM, и без него.

### 10.6. topic_switch без LLM

Если `needs_history()` вернул `False` при непустой истории, либо `CONTEXTUALIZATION_ENABLED=false`, либо LLM отработала с fallback, флаг `topic_switch` вычисляется детерминированно по слотам. LLM в этих случаях не вызывается, и без такого правила флаг всегда оставался бы `false`. Тогда после «прогрева гидросистемы» вопрос «Какая трудоемкость СО?» оставил бы в состоянии узел «гидросистема».

Предметные слоты: `node`, `maintenance_level`, `operation`, `part`. Сравниваются слоты `DialogState` (до обновления) и `entities` текущего вопроса после `canonicalize()`.

```python
SUBJECT_SLOTS = ("node", "maintenance_level", "operation", "part")

def topic_switch_by_slots(state: DialogState, ent: Entities) -> bool:
    prev = {k: getattr(state, k) for k in SUBJECT_SLOTS if getattr(state, k)}
    if not prev:                       # состояние пустое — переключаться не с чего
        return False
    cur = {k: getattr(ent, k) for k in SUBJECT_SLOTS if getattr(ent, k)}
    shared = any(prev.get(k) == v for k, v in cur.items())
    return not shared                  # нет ни одного общего предметного слота → новая тема
```

Где применяется:

| Путь | Источник `topic_switch` | `topic_switch_source` |
|---|---|---|
| история пустая | всегда `false` | `none` |
| `needs_history()=False`, история есть | `topic_switch_by_slots()` | `slots` |
| `needs_history()=True`, LLM ответила, проверка прошла | значение от LLM | `llm` |
| `needs_history()=True`, fallback (таймаут, JSON, проверка) | `false` — состояние сохраняется, вопрос зависимый | `none` |
| `CONTEXTUALIZATION_ENABLED=false`, история есть | `topic_switch_by_slots()` | `slots` |

Правило по слотам **не применяется**, когда сработал фильтр `needs_history()`: в эллипсисе («А для СО?» после ТО-1) общих слотов тоже нет, но тема продолжается. Для зависимых вопросов решение остаётся за LLM.

Проверка на фикстурах A.2 (состояние строится по пользовательским репликам истории, см. приложение A, «Правила сопоставления»):

|---|---|---|---|
| d017 | пусто («виды ТО» — только `topic`) | ТО-1 | `false` (состояние пустое) |
| d018 | гидросистема, прогрев рабочей жидкости | фургон, санитарная уборка | `true` |
| d019 | фургон, санитарная уборка | пусто (только `topic`) | `true` |
| d020 | ТО-1 | платформа | `true` |
| d021 | СО | гидросистема, бак гидросистемы | `true` |
| d022 | ТО-1 | шасси | `true` |
| d026 | ЕО | гидросистема, бак гидросистемы | `true` |
| d029 | СО | гидросистема, ТО-1 | `true` |

Если на этапе 0 окажется, что «виды ТО» в глоссарии дают `maintenance_level`, d017 даст `true`. В этом случае `topic`-термины («техническое обслуживание», «виды ТО») не должны заполнять предметные слоты — исправлять глоссарий, а не правило.

## 11. Canonicalization

### 11.1. Глоссарий

`scripts/build_canonical_glossary.py`:
- разбирает строки `[глоссарий]` из блока «ГЛОССАРИЙ И СИНОНИМЫ» RAG V3 (формат — по результатам этапа 0);
- объединяет их с `glossary_extra.yaml`;
- пишет `glossary_canonical.yaml`;
- падает с понятной ошибкой, если строку не удалось разобрать (номер строки и текст).

Формат записи:

```yaml
- canonical: "рабочая жидкость"
  type: part            # node | level | operation | part | parameter | condition | topic | product
  node: "гидросистема"
  abbr: []
  variants: ["гидрожидкость", "гидравлическое масло", "масло гидросистемы"]
```

`glossary_extra.yaml` заполняется вручную, только терминами из текста RAG V3. Минимум — термины, без которых не различаются пары из приложения A.4: виды ТО и их варианты; операции (подготовка к выезду, после запуска двигателя, после окончания работы, прогрев рабочей жидкости, санитарная уборка / обработка, проверка гидрожидкости на воду / на загрязнение, осмотр пальцев крепления гидроцилиндров, освидетельствование); части (бак гидросистемы, мерное стекло, картер двигателя, страхующие упоры, платформа); параметры (трудоемкость, температура, содержание воды, масса загрязнений, класс чистоты, уровень); условия («зима»: зимой, на морозе, при отрицательной температуре); синонимы «кузов (внутри)» → «фургон», «санобработка», «мойка» → «санитарная обработка».

Название изделия («автолифт», «АЛ 3У-М6», «оборудование», «спецоборудование», «надстройка», «изделие») получает `type: product`, даже если строка `[глоссарий]` описывает его как отдельный термин (в RAG V3 есть запись «оборудование»). Термины `product`:
- не заполняют слоты `Entities` и не дают `node`;
- удаляются из `residual`;
- не считаются предметными в правиле 4 раздела 10.2.

Иначе ключи группы g06 разъедутся: «…предусмотрены для оборудования?» получит лишний слот или остаток. Модульный тест: для трёх вопросов g06 `canonical` одинаков, а термин «оборудование» найден и помечен как `product`.

### 11.2. intent_rules.py

Intent по правилам, порядок проверки фиксированный (первое совпадение):

0. `parameter_value` — **вопрос о предельном значении**. Срабатывает, если одновременно есть:
   - маркер количества: «сколько», «скольки», «какую температуру», «какая температура», «какое значение», «до какой», «до каких»;
   - маркер ограничения: «нельзя», «запрещ», «превыша», «не более», «не менее», «не меньше», «не выше», «не ниже», «выше», «ниже».

   Такой вопрос спрашивает число, а не запрет: «Какую температуру рабочей жидкости гидросистемы нельзя превышать?» (q25, d031), «Не меньше скольки минут прогревать…» (d035), «Выше скольки градусов нельзя нагревать…». Без маркера количества правило не срабатывает, и вопрос остаётся `safety`: «При каком уровне масла в баке запрещено эксплуатировать автолифт?» (q18) — «при каком уровне» в маркеры количества не входит, ответ на него — условие запрета.
1. `safety`: «запрещ», «нельзя», «можно ли», «допускается ли», «разрешается ли», «опасн»; а также токен «можно» или «нельзя» последним перед «?» («А без страхующих упоров платформу смотреть можно?»).
2. `procedure` (вопросы да/нет о действии): «нужно ли», «надо ли», «следует ли», «обязательно ли», «необходимо ли». Идёт после `safety`, чтобы не перебивать запреты.
3. `periodicity`: «как часто», «периодичн», «интервал», «через сколько», «раз в», «когда проводится», «когда нужно проводить».
4. `parameter_value`: «сколько», «какова», «каков», «какая норма», «норма», «трудоемкость», «пропорция», «максимальн», «до скольки», «какую температуру».
5. `parts`: «какие детали», «какие запчасти», «что заменить».
6. `procedure`: «как», «что нужно», «что делать», «в каком порядке», «какие работы», «что входит», «кто допускается», «где».
7. иначе `other`.

Маркеры сравниваются по токенам и парам токенов `cleaned`/`standalone` в нижнем регистре, основы («запрещ», «превыша») — как префикс токена.

Правила применяются к `standalone`. Если LLM вернула другой intent, побеждает правило; расхождение пишется в лог (`intent_source="rules"`). Если правила не сработали, берётся intent от LLM.

### 11.3. canonicalize()

Шаг [6].

1. Токенизация, лемматизация `pymorphy3.MorphAnalyzer()` (один экземпляр на процесс, `lru_cache`).
2. Поиск терминов глоссария по n-граммам лемм, от длинных к коротким; найденные токены выбывают.
3. Нечёткий поиск `rapidfuzz.process.extractOne(..., scorer=fuzz.ratio, score_cutoff=FUZZY_CUTOFF)` (88) для оставшихся токенов длиной от 5 символов. Аббревиатуры (ЕО, СО, ТО-1, КОМ, АКБ) — только точное совпадение.
4. Заполнение слотов `Entities` по типам найденных терминов. Слоты от LLM проверяются: значение должно быть в глоссарии, иначе обнуляется с предупреждением. При конфликте побеждает глоссарий.
5. `node` выводится из поля `node` найденного термина, если не задан явно.
6. Нормализация `period` — функция `normalize_period()`, одна на нормализатор и уровень Q-A:
   - **интервал**: «один раз в год», «раз в год», «ежегодно» → `1 год`; «раз в три года» → `3 год`; «2 месяца», «через 2 месяца» → `2 месяц`; «250 ч», «250 часов», «250 моточасов» → `250 ч`;
   - **частота** (больше одного раза за период): «два раза в год», «2 раза в год» → `2/год`; «два-три раза в неделю», «2–3 раза в неделю» → `2-3/неделя`; «ежедневно», «каждый день» → `1/день`;
   - числительные словами («два», «три») приводятся к цифрам; тире и дефис между числами → `-`;
   - **вопросительные формы значения не дают**: «сколько раз в год», «раз в сколько лет», «через сколько часов», «как часто» → `period` пустой. Иначе вопрос «Сколько раз в год делают СО?» получил бы `1 год` и конфликтовал бы с ответом `2/год`;
   - функция идемпотентна: `normalize_period("2/год") == "2/год"`. Уровень Q-A проверяет ей формат `period` в своей базе.
7. Числа с единицами из вопроса — в слот `numbers` (отсортированный список).
8. Каноническая строка из слотов, а не из «мешка слов»:

```
canonical = "|".join([
  intent, node or "-", maintenance_level or "-", operation or "-", part or "-",
  parameter or "-", condition or "-", period or "-", ",".join(numbers) or "-",
  neg_flag,          # "neg", если в вопросе есть отрицание, иначе "-"
  residual,          # см. ниже
])
```

`residual` — отсортированные леммы оставшихся содержательных слов. Он заполняется **только** если все слоты `operation`, `part`, `parameter` пустые. Это защищает от схлопывания разных вопросов при неполном глоссарии. При заполненных слотах `residual = "-"`, и перефразировки совпадают.

9. `cache_key = sha256(f"{normalizer_version}|{kb_version}|{canonical}")`.

`NORMALIZER_VERSION` повышается при любом изменении промпта, правил или глоссария. `kb_version` меняется автоматически при изменении `DATA_FILE`.

Если на перефразировках из приложения A.3 ключи расходятся, исправлять в первую очередь `glossary_extra.yaml` и `intent_rules.py`, а не алгоритм.

## 12. Семантический кэш

Шаг [8]. Все пороги и режимы — переменные группы «Кэш» (6.3).

1. **Изоляция от старой базы.** Записи, созданные на `docs.txt`, не должны возвращаться. Имя индекса — `CACHE_INDEX_PREFIX` + `kb_version`. Старый индекс не удалять автоматически, а описать в README, как его очистить.
2. **Вектор** строить по `standalone`. В записи хранить `raw`, `standalone`, `canonical`, `intent`, `node`, `maintenance_level`, `normalizer_version`, `kb_version`.
3. **Фильтры** при поиске (`SEMANTIC_CACHE_FILTERS_ENABLED=true`): `intent`, `node`, `maintenance_level`, `normalizer_version`, `kb_version` (пустое значение тоже фильтр: `-` совпадает только с `-`). Фильтр по `maintenance_level` обязателен: «Как часто проводится ТО-1?» и «Как часто проводится СО?» почти совпадают по эмбеддингам. Если кэш не поддерживает фильтры, добавить поля в схему индекса, при несовместимом изменении — новый индекс.
4. **Точный кэш** (`EXACT_CACHE_ENABLED`). При `CANONICALIZATION_ENABLED=false` сохраняется текущий путь: хеш сырого вопроса + косинусный поиск (с изоляцией по `kb_version`). При `CANONICALIZATION_ENABLED=true` первый уровень — lookup по `cache_key` из слотов, затем семантический поиск с фильтрами; хеш сырого вопроса в этом режиме не используется. При попадании первого уровня семантический поиск не выполняется.
5. **Не кэшировать:** `needs_clarification=true` (включая подтверждение исправления ввода); `rewrite_source="fallback"` при `depends_on_history=true`, если `CACHE_STORE_FALLBACK=false`; ответы `direct` и `hybrid` уровня Q-A; ответы, в которых ассистент сообщил об отсутствии информации в документе (например, вопрос про шасси, d022).
6. **Пороги, top-k и TTL** — `SEMANTIC_CACHE_MIN_SIMILARITY`, `SEMANTIC_CACHE_STRICT_MIN_SIMILARITY`, `SEMANTIC_CACHE_TOP_K`, `SEMANTIC_CACHE_TTL_S`; значения по умолчанию — текущие из кода, не менять. Пороги кэша — **сходство** (больше — ближе), пороги уровня Q-A — **расстояние** (меньше — ближе, `QA_*_MAX_DISTANCE`). Переносить значения между ними нельзя: `QA_DIRECT_MAX_DISTANCE=0.12` не означает порог кэша 0.12. Если внутри кода нужна конвертация, она одна, в `settings.py` или в адаптере хранилища, с тестом. `scripts/eval_cache_threshold.py` на парах приложения A.4 и группах A.3 считает ложные попадания и промахи для набора порогов **с фильтрами и без**, отчёт в `reports/`.
7. Запись в кэш — после генерации, по `standalone` и `cache_key`.
8. При `SEMANTIC_CACHE_ENABLED=false` семантический поиск не выполняется, точный кэш работает по `EXACT_CACHE_ENABLED`. Оба флага `false` — кэш полностью выключен (нужно для пакетных прогонов, где важен свежий ответ LLM).
9. В трассировке (раздел 16) шаг [8] показывает: ключ точного кэша, результат, top-`TRACE_SHOW_CANDIDATES` кандидатов семантического кэша со сходством, применённые фильтры и порог сходства.

# Часть III. Уровень проверенных ответов (Q-A)

## 13. Алгоритм уровня Q-A

Шаг [7]. Файл базы — `QA_BASE_FILE` (приложение B), тесты — `QA_TESTS_FILE` (приложение C). Все пороги и режимы уровня — переменные группы «Q-A» (6.3): `QA_DIRECT_MAX_DISTANCE`, `QA_HYBRID_MAX_DISTANCE`, `QA_MIN_MARGIN`, `QA_TOP_K`, `QA_REQUIRE_VERIFIED`, `QA_STOP_RULES_ENABLED`, `QA_HYBRID_NUMBER_CHECK`.

### 13.1. Режимы работы (`QA_MODE`)

| Значение | Поведение |
|---|---|
| `off` | Уровень не вызывается (то же, что `QA_LAYER_ENABLED=false`) |
| `shadow` | Решение вычисляется и пишется в лог, но пользователь всегда получает ответ RAG. Для безопасной проверки на реальных вопросах |
| `hybrid_only` | `direct` понижается до `hybrid`: проверенный ответ всегда идёт через генерацию |
| `full` | `direct` и `hybrid` по правилам 13.2–13.10 |

По умолчанию после включения флага — `shadow`.

### 13.2. Индекс

Для каждой активной записи в коллекцию добавляются отдельные векторы:
- `question` (`kind=question`);
- каждая строка из `paraphrases` (`kind=paraphrase`).

Метаданные вектора: `qa_id`, `answer_group` (если нет — равен `qa_id`), `kind`, `intent`, `node`, `maintenance_level`, `condition`, `period` (список, в метаданных Chroma — строка через `;`), `canonical`, `verified` (bool), `kb_version`, `base_sha`.

Эмбеддинги считаются той же функцией, что использует основная коллекция Chroma в `assistant_api`. Модель эмбеддингов записывается в manifest. Если при запуске модель отличается от записанной, уровень отключается до пересборки.

Для каждого вектора `canonical` вычисляется функцией `canonicalize()` из модуля нормализации. Слоты записи (`intent`, `node`, `maintenance_level`, `condition`, `period`) берутся **из YAML, а не из `canonicalize()`**: это проверенная человеком разметка. Расхождения между слотами YAML и результатом `canonicalize()` для вопроса записи `validate` выводит как **предупреждения**, сборку они не останавливают. Часть таких предупреждений ожидаема: например, у qa004 в YAML `period: 2/год`, а в вопросе «Как часто проводится СО?» значения нет, и `canonicalize()` вернёт пустой `period`. Предупреждения нужны, чтобы видеть, что поправить в глоссарии, а не для того, чтобы их обнулять.

Формат значений слотов YAML при этом проверяется строго (раздел 14, ошибка 9): если `period` записи записан не в том формате, что выдаёт нормализатор, слот запроса никогда с ним не совпадёт и кандидат будет отброшен. Так ошибка формата превратилась бы в тихую потерю записи.

### 13.3. Шаги

1. **Точное совпадение.** Если `normalized.canonical` совпадает с `canonical` вектора записи и проверка слотов (13.4) пройдена, это кандидат с `distance = 0`.
2. **Семантический поиск.** Top-k (`QA_TOP_K=5`) векторов по `standalone`, косинусное расстояние. Результаты группируются по `qa_id`, для записи берётся минимальное расстояние.
3. **Проверка слотов** (13.4) для каждого кандидата. Не прошедшие отбрасываются.
4. **Отрыв.** `margin = d2 − d1`, где `d1` — расстояние лучшего кандидата, `d2` — лучшего кандидата **из другой `answer_group`** (если его нет, `margin = ∞`). Записи без `answer_group` образуют группу из одной записи. Записи одной группы имеют одинаковый по содержанию ответ (qa002 и qa003: оба содержат «2 месяца или 250 ч»), поэтому их близость не должна мешать `direct`.
5. **Решение:**

| Условие | Решение |
|---|---|
| нет кандидатов после проверки слотов | `none` |
| `d1 ≤ QA_DIRECT_MAX_DISTANCE` и `margin ≥ QA_MIN_MARGIN` и `intent` совпадает и запись проверена (13.5) | `direct` |
| `d1 ≤ QA_HYBRID_MAX_DISTANCE` | `hybrid` |
| иначе | `none` |

`QA_MODE=hybrid_only` понижает `direct` до `hybrid`, `shadow` — всё до «только лог».

### 13.4. Проверка слотов

Слоты запроса — из `normalized.entities` и `normalized.intent`.

- `maintenance_level`, `node`: если значение задано **и в запросе, и в записи** и они различаются, кандидат отбрасывается.
- `period`: в записи — одно значение или список. Если значение задано в запросе и в записи и значения запроса **нет в списке** записи, кандидат отбрасывается. Значение запроса берётся из `canonicalize()` по правилу 11.3 (п. 6). Вопросительные формы («сколько раз в год», «раз в сколько лет») значения не дают. Если в запросе значение пустое, проверка пройдена: вопрос «Как часто санобработка фургона?» не обязан содержать «ЕО».
- `condition`: должен совпадать **точно**, включая пустое значение. Иначе «Трудоемкость ЕО?» совпадёт с записью про зиму (qa006), а «Трудоемкость ЕО зимой?» — с общей записью (qa005).
- `intent`: несовпадение не отбрасывает кандидата, но запрещает `direct` (максимум `hybrid`). Причина: intent запроса определяется правилами и может расходиться с разметкой записи («Как промывают фильтроэлемент?» → `procedure`, запись qa022 — `parameter_value`).
- Числа из запроса (`numbers` в канонизации): если в запросе есть число с единицей, которого нет ни в `question`, ни в `paraphrases`, ни в `answer` записи, `direct` запрещается. Пример: «ветер 25 м/с» и запись qa049 с «20 м/с» → `hybrid`, чтобы генерация ответила «нет, допустимо не более 20 м/с».

### 13.5. Проверенность записи

- `verified_by: draft-ai` — запись подготовлена автоматически и человеком не проверена.
- При `QA_REQUIRE_VERIFIED=true` (по умолчанию) такие записи не могут дать `direct`, максимум `hybrid`.
- Проверка записи человеком — команда `qa_tool verify <id> --by "Фамилия"`: она проставляет `verified_by` и `verified_at` в YAML.
- Для автотестов используется `QA_REQUIRE_VERIFIED=false` (флаг `--ignore-verified` у команды `test`).

### 13.6. Общие записи и записи с условием

Если для одного вопроса есть общая запись (`condition: null`) и запись с условием (например, qa005 и qa006 — ЕО и ЕО зимой), значения, относящиеся только к условию, в общую запись не включаются ни в `answer`, ни в `facts`. Иначе на вопрос «Сколько длится ЕО?» `direct` выдаст и зимнюю норму, хотя пара c02 проверяет, что зимняя запись на общий вопрос не отдаётся. Общая запись может только сообщить, что для условия есть отдельная норма. Обратное допустимо: запись с условием может упоминать общее значение для сравнения (qa006).

Проверяется командой `validate` (раздел 14, ошибка 10).

### 13.7. Стоп-правила вне корпуса

Выполняются до поиска при `QA_STOP_RULES_ENABLED=true`. Если правило сработало, решение `none` с причиной в логе, кандидаты не ищутся:

| Правило | Пример | Причина в логе |
|---|---|---|
| В запросе единица измерения, которой нет в `DATA_FILE`. Список единиц — словарь единиц нормализатора (10.1) за вычетом найденных в `DATA_FILE`; вычисляется при `build` и пишется в manifest | «давление … в МПа» (n02), «Н·м» | `unit_out_of_corpus` |
| В запросе вид ТО, которого нет в документе (`ТО-2`, `ТО-3` и т. п.; распознаётся по шаблону `ТО-\d` до обнуления слота) | «Когда проводится ТО-2?» (n04) | `level_out_of_corpus` |

Без этих правил n02 близок к qa043 («подтягивать соединения под давлением»: тот же узел «гидросистема»), и удержание нуля ложных попаданий зависело бы только от порога и отрыва. Правила не заменяют калибровку: остальные `no_match` по-прежнему проверяются порогами.

### 13.8. Устаревание

`kb_version` — sha256 содержимого `DATA_FILE`, первые 12 символов (как в разделе 11.3). Если `kb_version` в manifest не совпадает с текущим, уровень **отключается целиком**: все запросы идут в RAG, в лог пишется предупреждение, `stats` показывает «база устарела». Включается снова только после `validate` и `build`.

### 13.9. direct

```
{answer}

Источник: п. {source через запятую}. Проверенный ответ ({qa_id}).
```

Если в `source` есть `4`, выводится «разд. 4».

### 13.10. hybrid и единый шаблон генерации

Для всех режимов, кроме базовой линии, используется **один** шаблон `prompts/generate_extended_ru.txt` с необязательными блоками. Отдельных шаблонов «с историей» и «с проверенным ответом» нет: при `hybrid` с историей нельзя выбирать между двумя файлами. При всех выключенных флагах используется исходный шаблон проекта без изменений (раздел 4).

| Блок | Когда включается |
|---|---|
| `{verified_block}` — проверенный ответ и правила 1–3 | решение Q-A `hybrid` |
| `{history_block}` — краткая история | нормализация включена и история не пустая |
| `{standalone_line}` — уточнённый вопрос | `standalone` отличается от текста после шага [2] |

Отсутствующий блок заменяется пустой строкой целиком, вместе с заголовком; пустых заголовков («История: ») в промпте быть не должно (тест). Шаблон:

```
Ты отвечаешь на вопрос по руководству ТО автолифта АЛ 3У-М6.
Используй только фрагменты документа{verified_intro}.

Правила:
{verified_rules}
- Числа, единицы, сроки и нормы бери ТОЛЬКО из фрагментов{verified_or}, дословно.
- Если в фрагментах нет ответа — так и скажи, ничего не придумывай.
- Укажи пункт документа.

{verified_block}
Фрагменты: {chunks}
{history_block}
Вопрос: {raw}
{standalone_line}
```

Значения блоков при `hybrid`:

```
verified_intro  = " и проверенный ответ на близкий вопрос"
verified_or     = " или проверенного ответа"
verified_rules  = "- Если проверенный ответ отвечает на вопрос — опирайся на него.
                   - Если вопрос отличается (другое условие, другое число), ответь по смыслу
                     проверенного ответа и фрагментов, явно указав норму из документа."
verified_block  = "Проверенный ответ ({qa_id}, пп. {source}): {answer}"
```

Без `hybrid` все четыре значения пустые. `history_block = "История: {history}"`, `standalone_line = "Уточнённый вопрос: {standalone}"`.

После генерации выполняется **проверка чисел** (`QA_HYBRID_NUMBER_CHECK`). Направление проверки: **каждое число с единицей в ответе модели** должно встречаться в проверенном ответе или в переданных фрагментах. Числа из самого вопроса (`raw`, `standalone`) тоже допустимы: для t049 («ветер 25 м/с», норма документа — 20 м/с) ответ «при 25 м/с работать нельзя, допускается не более 20 м/с» проходит, а выдуманное «30 м/с» — нет. Обратная проверка (все числа проверенного ответа есть в ответе модели) не выполняется: проверенный ответ может содержать значения, не относящиеся к уточнённому вопросу. Если проверка не прошла, ответ генерируется заново тем же шаблоном без блока Q-A (`verified_*` пустые), а случай пишется в лог (`hybrid_number_mismatch`).

## 14. Валидация базы (`qa_tool validate`)

**Ошибки** (сборка запрещена):
1. YAML не соответствует схеме; отсутствуют обязательные поля; `schema_version` не поддерживается. Поддерживается только `schema_version: 2` для `qa_base.yaml` и `qa_tests.yaml`; для версии 1 сообщение: «устаревший файл: нет answer_group / accept_ids / guard, возьмите версию из комплекта (MANIFEST.md)».
2. Дубликаты `id`; `id` не по шаблону `qa\d{3}`.
3. Значения `intent`, `node`, `maintenance_level`, `condition` вне допустимых списков (из приложения A; `maintenance_level` — только ЕО, ТО-1, СО).
4. Любой элемент `facts` не найден в `DATA_FILE` или не найден в `answer`. Сравнение без учёта регистра, после нормализации: NFKC, неразрывный пробел → пробел, «−» и «–» → «-», схлопывание пробелов.
5. В `answer` есть число (`\d+(?:[.,]\d+)?`), которого нет в `DATA_FILE`.
6. В `answer` есть «ТО-2», «МПа» или «Н·м».
7. `source` ссылается на пункт, заголовка которого нет в `DATA_FILE` (поиск `^{пункт}\.` или `^{пункт} `; «4» — заголовок раздела 4 документа).
8. Одинаковые `question` или `paraphrase` (после нормализации) у разных записей.
9. Значение `period` (или элемент списка) не равно результату функции нормализации периода из раздела 11.3 (п. 6), применённой к нему самому, то есть записано не в каноническом формате. Допустимые формы: `N месяц`, `N ч`, `N год`, `N/год`, `N-M/неделя`, `N/день`.
10. Нарушено правило 13.6: у общей записи (`condition: null`) в `facts` есть значение, которое есть в `facts` записи с тем же `intent` и `maintenance_level` и непустым `condition`, но отсутствует в `facts` других общих записей с тем же `intent` и `maintenance_level`.
11. Две записи из **разных** `answer_group` (или без группы) с одинаковыми `intent`, `maintenance_level`, `condition` и одинаковым множеством `facts`, у которых ответы похожи (`rapidfuzz.fuzz.token_set_ratio ≥ 85`). Это скрытый дубль: такие записи нужно объединить в группу или развести по содержанию. Пары с одинаковыми `facts`, но разными ответами (qa022 / qa023 — разные работы по 2 ч) не являются ошибкой.
12. В `qa_tests.yaml`: `expected_id`, `accept_ids`, `must_not` или `near` ссылается на несуществующую запись; `accept_ids` содержит запись не из той же `answer_group`, что `expected_id`.

**Предупреждения** (сборка разрешена):
1. Слоты YAML расходятся с результатом `canonicalize(question)`.
2. Две записи имеют одинаковый `canonical` у вопроса или перефразировки: вероятное ложное совпадение.
3. Тестовый вопрос из `qa_tests.yaml` совпадает с `question` или `paraphrase` базы (утечка теста в индекс).
4. `verified_by: draft-ai` — число непроверенных записей.
5. Пункты документа, на которые нет ни одной записи (покрытие).
6. Поле `kb_file` базы не совпадает с именем файла `DATA_FILE`. Это только подсказка: устаревание определяется по `kb_version` (13.8), а не по имени.

Вывод: таблица ошибок и предупреждений с `id` и причиной; код выхода `1` при ошибках. Флаг `--json` — машиночитаемый вывод.

### 15.6. `manual` — ручное тестирование (REPL)

```
qa_tool manual                         # свободный ввод вопросов

```

Для каждого вопроса выводится то же, что в `ask`, и запрашивается оценка:

```
Оценка: [y] верно  [n] неверно  [p] частично  [s] пропустить  [c] комментарий  [q] выход
```

При `n` или `p` дополнительно спрашивается правильный `qa_id` или `none`.

Команды REPL:
- `/history` — добавить реплики в историю (для проверки диалогов);
- `/reset` — очистить историю;
- `/show qaNNN` — показать запись;
- `/mode full|hybrid_only` — сменить режим;
- `/stats` — сводка текущей сессии;
- `/quit` — выход.

Результаты пишутся построчно в `reports/qa/manual_YYYYMMDD_HHMM.jsonl`: вопрос, история, решение, кандидаты, оценка, правильный id, комментарий, время. При выходе формируется `manual_YYYYMMDD_HHMM.md` с итогами: число оценок, доли y/n/p по типам решений, список ошибок.

### 15.7. `test` — автоматическое тестирование

```
qa_tool test [--type match|contrast|no_match|dialog] [--ignore-verified] [--mode full]
             [--fail-under-match 0.9] [--json] [--with-generation]
```

Для каждого теста выполняется `lookup` и сравнение с ожиданием:

| Тип | Пройден, если |
|---|---|
| `match` | решение `direct` или `hybrid` и `qa_id ∈ {expected_id} ∪ accept_ids` (если задан `expected_mode`, режим тоже совпадает) |
| `contrast` | `qa_id ∈ {expected_id} ∪ accept_ids` или решение `none`; `qa_id` не входит в `must_not` |
| `no_match` | решение `none`; если задан `guard`, причина в логе должна совпасть (13.7) |
| `dialog` | после нормализации с историей `qa_id == expected_id`; при `expected_clarification: true` — `needs_clarification=true` и уровень не вызывался; при выключенной contextualization — `skipped` |

`accept_ids` допускаются только из той же `answer_group` (проверяет `validate`). Точное попадание в `expected_id` для тестов с `accept_ids` выводится в отчёте отдельной строкой, без порога.

Дополнительно для `direct` проверяется, что ответ содержит все `facts` записи. С флагом `--with-generation` для `hybrid` вызывается генерация и выполняется проверка чисел из 13.10.

Метрики отчёта:
- точность `match` (top-1) и доля `direct` / `hybrid` / `none` среди них;
- `contrast`: число путаниц внутри пар (главная метрика) и доля `none`;
- `no_match`: доля ложных попаданий и id, на которые они пришлись;
- `dialog`: пройдено / провалено / пропущено (этап B);
- `no_match`: сколько отсечено стоп-правилами 13.7, сколько порогами;
- распределение расстояний для верных и ошибочных решений;
- задержка уровня: p50 и p95, отдельно время эмбеддинга.

Отчёты: `reports/qa/test_YYYYMMDD_HHMM.md` и `.json`. Код выхода `1`, если нарушен любой порог раздела 22.

### 15.9. `clear` — очистка

```

### 15.10. `calibrate` — подбор порогов

```

```

# Часть IV. Наблюдаемость и тестирование

## 16. Режим трассировки

### 16.1. Назначение

Режим показывает, как вопрос меняется от исходной формулировки до текста, который реально уходит в LLM, и какое решение принято на каждом шаге. Трассировка выводится **отдельным блоком**, не смешивается с ответом ассистента и с обычным логом.

Режим включается переменной `TRACE_MODE` (6.3) или командой консоли `/trace off|summary|full` (раздел 8). Аргумент CLI `--trace` имеет приоритет над переменной.

| `TRACE_MODE` | Что выводится |
|---|---|
| `off` | ничего (по умолчанию) |
| `summary` | короткая цепочка текстов: raw → после [2] → standalone → canonical → решение Q-A / кэша → источник ответа; одна строка на шаг |
| `full` | все шаги [0]–[11] с полями, кандидатами, расстояниями, временем и точным содержимым запроса к LLM |

`TRACE_OUTPUT`: `console` (stderr, чтобы ответ в stdout оставался чистым), `file` или `both`. При `file` / `both` блок пишется в `TRACE_FILE` (JSONL, одна строка на запрос) и в соседний `.md` с тем же содержимым в читаемом виде.

### 16.2. Формат блока

Пример (`TRACE_MODE=full`, вопрос введён в латинской раскладке, в истории — вопрос «Какова трудоемкость ТО-1?» и ответ на него). Значения условные, формат обязателен.

     │ system: Ты — ассистент по техническому обслуживанию автолифта…
     │ user:   Проверенный ответ: …
     │         Фрагменты документа: [ch_031] … [ch_032] …
     │         Вопрос: Какова трудоемкость сезонного обслуживания?
     └──────────────────────────────────────────── 1 834 симв.
[11] answer             source=hybrid(qa008), 1 410 мс, в кэш: нет, state: level=СО
═════════════════════════════════════════════════════════
```

Требования:
1. Шаги нумеруются так же, как в пайплайне (раздел 5) и в логе (раздел 18): `step_id` от 0 до 11. Пропущенный шаг выводится с причиной («пропущен: needs_history=False», «пропущен: direct»), а не исчезает.
2. На каждом шаге, где текст меняется, выводится новый текст целиком. Если текст не изменился — пометка «без изменений».
3. Шаг [10] показывает **точное** содержимое запроса к LLM генерации: модель, параметры, имя файла промпта и список `messages` после подстановки. При `TRACE_SHOW_PROMPT=false` выводятся только длины. Запрос нормализатора (шаг [4]) показывается так же в режиме `full`.
4. Длинные поля (ответы истории, фрагменты, системный промпт) обрезаются до `TRACE_MAX_CHARS` с пометкой «… (+N симв.)». В файл JSONL пишется полный текст, если `TRACE_MAX_CHARS=0`.
5. Ключи API, токены и заголовки авторизации маскируются (`sk-…****`). Тест проверяет, что в блоке нет значений переменных с `KEY`, `TOKEN`, `SECRET` в имени.
6. Число кандидатов Q-A, кэша и ретривера в блоке — `TRACE_SHOW_CANDIDATES`.
7. При `confirm` (шаг [2]) блок заканчивается на [2] с пометкой «ответ пользователю: уточнение», при `needs_clarification` — на [5].
8. `TRACE_COLOR=auto|on|off` — подсветка шагов в консоли; в файл цвет не пишется.
9. Трассировка не меняет поведение пайплайна: ответы с `TRACE_MODE=off` и `full` совпадают (тест).

### 16.3. Реализация

- Модуль `assistant_api/trace.py`: объект `Trace` создаётся на запрос, каждый шаг вызывает `trace.step(step_id, name, **fields)`; вывод — `render_console()`, `render_md()`, `to_json()`.
- Тот же объект используется пакетным прогоном (раздел 17, `BATCH_TRACE`) и командой `qa_tool ask --trace`.
- Консольная команда `/trace last` повторно печатает блок последнего запроса.

## 17. Пакетное тестирование из файла

### 17.1. Запуск

```
python -m assistant_api.batch [--input FILE] [--stage STAGE] [--profiles env/baseline.env,env/full.env] [--trace] [--limit N]
```

Все параметры имеют переменные окружения группы `BATCH_*` (6.3); аргументы CLI их перекрывают. В начале прогона печатается итоговая конфигурация (как `--print-config`) и сохраняется в отчёт.

### 17.2. Входные форматы

Формат определяется по расширению или `BATCH_FORMAT`.

| Формат | Структура |
|---|---|
| `txt` | один вопрос на строку; пустая строка — граница диалога (вопросы внутри блока идут с общей историей); строка с `#` — комментарий; ожиданий нет |
| `yaml` | список `items`: одиночные вопросы и диалоги с ожиданиями (пример — `batch_example.yaml`) |
| `jsonl` | одна строка — один элемент той же схемы, что в `yaml` |
| `csv` | колонки `id, dialog_id, turn, question, a, input_fix_action, input_fix_kinds, input_fix_text, standalone_contains, intent, qa_id, decision, expected_contains, not_contains`; списки через `;` |

Схема элемента `yaml` / `jsonl`:

```yaml
- id: b001                       # обязательное
  tags: [layout, to1]            # для BATCH_FILTER_TAGS
  turns:                         # 1 и более реплик; история накапливается по порядку
    - q: "Rfr xfcnj ghjdjlbncz NJ-1&"
      expect:                    # все поля необязательные
        input_fix:
          action: auto           # none | auto | confirm | answer_with_note
          kinds: [layout]        # homoglyph | capslock | layout
          text: "Как часто проводится ТО-1?"
        standalone_contains: ["ТО-1", "период"]
        intent: periodicity
        qa_id: [qa002, qa003]    # допустимые записи
        decision: hybrid         # direct | hybrid | none
        expected_contains: ["2 месяц"]   # в ответе (только stage=full)
        not_contains: ["ТО-2"]
        clarification: false
```

### 17.3. Стадии

`BATCH_STAGE` ограничивает, до какого шага выполняется пайплайн:

| Стадия | Шаги | LLM | Что проверяется |
|---|---|---|---|
| `input_fix` | [0]–[2] | нет | `input_fix` |
| `normalize` | [0]–[6] | только нормализатор | + standalone, intent, слоты, clarification |
| `qa` | [0]–[7] | только нормализатор | + `qa_id`, `decision` |
| `retrieve` | [0]–[9] | только нормализатор | + id чанков (если заданы `chunks`) |
| `full` | [0]–[11] | да | + `expected_contains`, `not_contains` в ответе |

Проверяются только ожидания, относящиеся к выполненным шагам; остальные получают статус `skipped`.

### 17.4. История

`BATCH_HISTORY_MODE`:
- `live` — в историю пишутся фактические ответы ассистента;
- `fixed` — если у реплики задан `a:` (эталонный ответ ассистента), в историю пишется он; так результат нормализации не зависит от качества генерации. Для `stage` ниже `full` используется всегда `fixed`, при отсутствии `a:` — заглушка «(ответ не сгенерирован)».

Каждый диалог начинается с пустой истории и пустого `DialogState`.

### 17.5. Профили и сравнение

- `BATCH_PROFILES=env/baseline.env,env/full.env` — прогон одного файла с разными профилями переменных (6.1); профиль накладывается поверх текущей конфигурации, CLI по-прежнему имеет приоритет. Отчёт содержит таблицу «вопрос × профиль».
- `BATCH_COMPARE_WITH=reports/batch/<ts>` — сравнение с прошлым прогоном: что стало лучше, хуже, изменились ли ответы.
- `BATCH_REPEAT=N` — повтор каждого вопроса N раз для оценки стабильности нормализатора (доля одинаковых standalone и canonical).

### 17.6. Отчёты и код выхода

Каталог `BATCH_OUTPUT_DIR/<YYYYMMDD_HHMMSS>/`:
- `results.jsonl` — по строке на реплику: вход, все промежуточные тексты, решения, ответ, проверки, время шагов;
- `summary.md` — конфигурация, число вопросов, доля пройденных проверок по видам, список провалов с короткой трассировкой, медиана и p95 времени по шагам;
- `traces.jsonl` и `traces.md` — полные блоки трассировки (при `BATCH_TRACE=true`);
- `config.json` — итоговые значения переменных (ключи замаскированы).

Код выхода: `0` — все проверки пройдены или доля пройденных ≥ `BATCH_FAIL_UNDER`; `1` — ниже порога; `2` — ошибка входного файла. `BATCH_STOP_ON_ERROR=true` прерывает прогон на первом исключении.

### 17.7. Связь с другими прогонами

- Фикстуры приложения A и тесты `qa_tests.yaml` могут быть запущены через `batch` (конвертер `scripts/fixtures_to_batch.py`), но метрики приёмки считают специализированные скрипты: `eval_normalization.py` и `qa_tool test`.
- Файл «вопросы и ответы (TXT)» можно подать на вход `batch` как `txt` только при `QA_LAYER_ENABLED=false` (раздел 24).

## 18. Логирование

### 18.1. Лог пайплайна

`PIPELINE_LOG_FILE` (JSONL), одна строка на вопрос: `request_id`, `raw`, `input_fix` (`action`, `kinds`, `layout_ratio`, `text`, `unresolved_tokens`), `standalone`, `canonical`, `intent`, `intent_source`, `entities`, флаги, `rewrite_source`, `fallback_reason`, `topic_switch`, `topic_switch_source`, решение Q-A, результат кэша (`exact_hit` / `semantic_hit` / `miss`), расстояние при семантическом попадании, id чанков, `kb_version`, `normalizer_version`, время шагов по `step_id` (мс). Ключи API не логировать. Уровень подробности — `LOG_LEVEL`.

Лог и трассировка — разные вещи: лог пишется всегда и компактно, трассировка включается отдельно и содержит тексты промптов.

### 18.2. Лог уровня Q-A

`QA_LOG_FILE` (по умолчанию `logs/qa_layer.jsonl`), одна строка на вызов:

```json
{"ts": "...", "mode": "full", "raw": "...", "standalone": "...", "canonical": "...",
 "slots": {...}, "candidates": [{"qa_id": "qa017", "d": 0.08, "slots_ok": true}],
 "decision": "direct", "qa_id": "qa017", "d1": 0.08, "margin": 0.11,
 "reason": "within_direct", "latency_ms": 12, "embed_ms": 35, "kb_version": "..."}
```

Ключи API и персональные данные не писать.

Дополнительно в строке лога Q-A: `request_id` (общий с логом пайплайна) и `step_id: 7`.

### 19.4. Переменные окружения

- **Сверка списков.** Тест читает поля `Settings` и сравнивает их с переменными в `env.example` и с таблицами переменных в README: каждая переменная есть во всех трёх местах, лишних нет.
- **Влияние.** Для каждой переменной группы «Кэш», «Коррекция ввода», «Q-A» и `TRACE_MODE` — тест, что смена значения меняет наблюдаемое поведение (например, `SEMANTIC_CACHE_MIN_SIMILARITY=1.0` → попадания только для почти идентичного вектора, а при `0.0` любой кандидат с прошедшими фильтрами — попадание; `LAYOUT_FIX_ENABLED=false` → f01 не исправляется; `QA_MODE=shadow` → пользователь получает ответ RAG).
- **Приоритет** cli > env > `ENV_FILE` > `.env` > default на одном параметре.
- **Валидация.** Неверное значение (`TRACE_MODE=verbose`, `LAYOUT_AUTO_MIN_RATIO=1.5`, `LAYOUT_CONFIRM_MIN_RATIO > LAYOUT_AUTO_MIN_RATIO`) → ошибка запуска с именем переменной и допустимыми значениями.
- **Без хардкода.** Проверка (grep в CI): в модулях `normalization/`, `qa_layer/`, `batch/` нет числовых порогов кэша и Q-A вне `settings.py`.

### 19.5. Трассировка и пакетный прогон

- ответ при `TRACE_MODE=off` и `full` совпадает;
- в блоке трассировки есть шаги 0–11 (или пометки «пропущен»), шаг [10] содержит итоговый `messages`, в блоке нет секретов;
- `batch` на `batch_example.yaml` со стадией `input_fix` проходит без LLM; со стадией `normalize` — с моком LLM; форматы `txt`, `yaml`, `jsonl`, `csv` дают одинаковое число реплик для одного набора;
- код выхода `1` при `BATCH_FAIL_UNDER=1.0` и одном провале; `2` при битом файле.

## Приложение A. Фикстуры нормализации

Файлы `fixtures/*.yaml`. Используются модульными тестами, `eval_normalization.py` и (через конвертер) пакетным прогоном (17.7).

### Правила сопоставления

- `standalone_contains` — список основ. Элемент засчитывается, если с него начинается какой-либо токен standalone (без учёта регистра, после ё→е). Элементы с пробелом или цифрами («ТО-1», «2 месяц») ищутся как подстрока.
- `standalone_not_contains` — значения из ответов ассистента, которых не должно быть в standalone (проверка переноса ответа).
- Отрицание проверяется по токенам «не», «нельзя», «без», «запрещ*», а не по подстроке «не».
- Для `needs_clarification=true` проверяется `clarification_contains`, а `standalone_contains` не проверяется.
- `history_gate` — ожидаемый результат `needs_history()` (раздел 10.2). Проверяется модульным тестом без LLM.
- `negation_preserved: true` — в standalone есть хотя бы один из токенов «не», «нельзя», «без», «менее», «запрещ*».
- Основы в `standalone_contains` берутся только из вопроса пользователя и из объекта, на который указывает местоимение. Значения, способы и критерии из ответов ассистента — только в `standalone_not_contains`.
- Диалоги с `fallback_reason="timeout"` не входят в расчёт `standalone_contains` и считаются отдельной метрикой (доля таймаутов).
- **Состояние диалога для фикстуры.** Перед вопросом пользовательские реплики `history` прогоняются по порядку через `clean_text()` → `fix_input()` → `canonicalize()` → `update_state()` без LLM: все первые реплики в фикстурах самостоятельные. Так `DialogState` одинаков в модульных тестах и в прогоне с LLM.
- **topic_switch** проверяется во всех диалогах, где поле задано. В отчёте метрика выводится отдельно по источникам: `slots` (гейт не сработал, проверяется без LLM, модульным тестом) и `llm`. Диалоги с fallback по таймауту из метрики `llm` исключаются.
